# ServiceFlow 开发与面试手册

建议结合源码、接口结果和测试讲解。能够描述系统能力不等于拥有全部模块的原创贡献，个人工作应按实际提交和理解范围表达。

## 模块一：HTTP 与生命周期

实现入口是 FastAPI lifespan，启动时装配模型、记忆、知识库和监控，退出时关闭相应资源。`/chat` 使用 Pydantic 请求/响应模型。

面试深挖：为什么不用模块导入时连接数据库？同步调用为什么会阻塞异步服务？HTTP 200 是否代表业务成功？超时后重试会不会重复写入？

回答要点：生命周期便于控制资源和测试；同步 Chroma 调用通过 `to_thread` 移出事件循环，但线程池仍有容量上限；当前聊天没有完整幂等机制，应为外部写动作补充请求去重和状态机。

扩展知识：ASGI、协程调度、连接池、超时预算、背压、HTTP 状态码和依赖注入。

## 模块二：意图与路由

LLM、向量和规则提供不同类型的证据，细粒度意图映射到业务角色，混合问题再结合关键词与实体评分选择辅助角色。

深挖：为什么不全部交给 LLM？为什么低置信度要澄清？复合意图如何标注？权重 0.7/0.2/0.1 如何证明合理？

回答要点：当前权重是启发式默认值，需要通过固定数据集和消融验证；不将置信度视作真实概率。使用混淆矩阵查找 refund/billing 等边界错误，必要时采用多标签或结构化任务分解。

扩展知识：Precision/Recall/F1、类别不平衡、校准、数据泄漏、阈值与拒答策略。

## 模块三：Agent 与工具

角色通过契约、工具集合、提示词和编排位置区分；tool-use 循环把模型提出的工具调用转为受校验的代码执行，再返回结果。

深挖：Agent 与普通 LLM 调用有何区别？Skills 能阻止越权吗？工具异常或无限循环怎么办？多个 Agent 是否必然更好？

回答要点：能依据工具结果继续决策是关键，权限仍由代码强制；调用轮次和超时必须有限。当前系统主要是中心化路由编排，不是完全自治的多智能体社会。多角色只在任务拆分有价值时启用。

扩展知识：JSON Schema、最小权限、提示注入、工具幂等、审批、人机协作和审计。内部工具管理不等于标准 MCP 服务。

## 模块四：RAG 与成本

原查询保留用户完整表达，改写覆盖近义词和子主题，全部搜索同一个知识库。并行召回后合并，再尝试重排。

示例：用户问“重复扣款怎么退款、多久到账”，改写可分别覆盖“重复支付核验”“退款申请规则”“到账时间”。三个子查询不是查询三个 Agent，也不是查用户历史。

深挖：为什么并行？为什么保留原查询？多查询是否一定提高准确率？去重、切片和排序有什么问题？

回答要点：并行降低可重叠等待，不减少运算；改写可能偏离，原查询起保底作用。当前约 500 字切片未必适合所有文档，候选去重也需稳定 ID。用消融比较 Recall@K、回答依据、P95 与 Token 后再判断收益。

扩展知识：稀疏/稠密检索、混合召回、RRF、cross-encoder、上下文预算、chunk overlap 和来源引用。以上扩展不表示当前都实现。

## 模块五：记忆与一致性

近期消息用 Redis，摘要及长期片段/画像用 Chroma。压缩控制上下文长度，但会损失事实。画像后台更新不阻塞主回复。

深挖：如何防串用户？TTL 是否等于隐私删除？两个并发请求同时压缩会怎样？为何画像用 upsert？

回答要点：查询先按用户限定再按会话筛选；生产还必须从可信身份派生用户 ID。TTL 只覆盖对应 Redis key。并发压缩可能覆盖或重复，需会话锁、版本号或原子脚本；upsert 避免先删再写窗口，但不是完整并发控制。

扩展知识：Redis list/TTL、事务与 Lua、最终一致性、乐观锁、异步任务可靠性和数据保留政策。

## 模块六：缓存、熔断与降级

缓存减少相同工具请求，超时界定等待，熔断在持续失败时快速返回，fallback 提供可理解的失败结果。

深挖：缓存键包含什么？知识更新如何失效？半开状态能否只放一个探针？降级结果能否被当成成功缓存？

回答要点：键应包含查询参数、版本及权限范围；当前进程缓存不跨实例共享。HALF_OPEN 仍需并发门控，fallback 应明确标记不可作为真实证据。生产还需重试退避、抖动、并发隔离及全链路超时预算。

扩展知识：缓存穿透/击穿/雪崩、single-flight、负缓存、熔断与限流区别。

## 模块七：观测和评测

在线观察耗时与失败，离线比较质量。Accuracy、Judge 得分和用户满意度不是同一指标。

深挖：P95 为什么比平均值重要？Judge 可信度如何验证？回归基线为什么不能一直自动更新？一次调用如何定位问题？

回答要点：用 request_id 串联角色、工具与阶段计时；人工抽样复核 Judge，单列解析失败。保留固定审核基线，按错误类型比较。当前指标注册、冷启动告警和持久化 trace 仍有改进空间，不宣称完整可观测平台已经完成。

扩展知识：Counter/Gauge/Histogram、SLO、分位数、采样、离线与在线评估、实验显著性。

## 模块八：前端和部署

前端使用原生 HTML/CSS/JavaScript，维护用户/会话标识并调用同源 API；没有使用 React/Vue。本地 Nginx 提供页面，公网由演示网关提供页面和认证。

深挖：Cookie 和 localStorage 差别？HttpOnly 能防所有攻击吗？为什么同源？Docker 镜像与容器、卷有什么区别？

回答要点：会话凭据存 HttpOnly Cookie，localStorage 只保存非可信用户标识；SameSite 和 Origin 校验减少跨站写风险，不能代替所有 CSRF/XSS 防护。镜像是运行模板、容器是实例、卷保留数据；临时文件系统不适合生产长期记忆。

扩展知识：HTTPS、反向代理、CORS、CSRF、XSS、健康探针、多阶段构建、非 root、密钥注入、临时存储和发布回滚。

## 面试中回答“怎么优化”

先复述症状与度量，再给出可验证方案：

- 回复慢：分阶段计时，区分改写、召回、重排、角色合成、记忆压缩；随后考虑减少不必要调用和预算控制。
- 回答不准：先分流错误、检索错误、证据不足还是生成错误，不只改 Prompt。
- 费用高：记录各阶段用量，对简单问题跳过扩展，结合质量指标控制 Token 和候选。
- 并发低：明确演示的全局单并发保护；生产再考虑连接池、队列、隔离、幂等和水平扩容。
- 可靠性差：故障注入、可见降级、单探针熔断、可靠后台任务和真实存储备份。
- 想提高简历说服力：提交数据集、原始报告和失败案例，不填写未测得的百分比。
