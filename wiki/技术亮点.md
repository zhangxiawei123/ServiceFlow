# ServiceFlow 技术亮点与设计取舍

## 意图识别：多路径容错

LLM 适合理解语义，规则适合确定性实体及关键词，本地向量匹配提供低成本补充。融合分类结果后映射到业务组，再服务路由。

代价是规则、模板和模型可能互相冲突，置信度并非统计校准概率。改进应先分析混淆矩阵、类别分布和失败样本，再调权重、补样本或增加澄清策略。

## 多 Agent：职责和工具权限分离

通用、技术、账单和升级角色具有不同契约和工具范围。主辅角色并行后合成，让混合诉求不必由一个角色承担所有职责。

多角色增加模型调用与合成成本；对简单问题并行并不划算。应比较单角色与协作路径的任务覆盖率、费用和 P95，而不是以角色数量证明先进性。

## RAG：召回覆盖与排序分开

长文档按句子或换行聚合到约 500 字，超长单句可能超过该值；当前不是精确 Token 切分，也没有通用滑窗重叠。

原查询保留完整诉求，三个改写用于覆盖不同表达和子主题，全部查询同一个 Chroma 知识库。随后合并候选并重排，让更相关片段进入回答上下文。

并行改变等待方式，不让四次检索变成一次。向量化和检索消耗 CPU，改写和重排额外消耗模型 Token。缓存位于具体工具调用层，不能声称重复 RAG 请求完全不再调用改写或重排模型。

去重目前对整个候选项字符串做哈希；同一片段的 score 不同仍可能重复。后续应使用稳定 chunk_id 或规范化内容键。改写需增加结构校验、数量上限和去漂移约束；重排需校验唯一、合法索引并补齐遗漏候选。

## 工具可靠性：显式失败路径

工具管理器提供参数检查、超时、TTL 缓存、三态熔断及 fallback。业务 Agent 层另外控制白名单与调用轮次。

当前熔断的 HALF_OPEN 分支并未用锁严格限制单探针，高并发下会同时放行；缓存是进程级状态，没有分布式一致性或租户键空间。生产需要单探针门控、并发限制、带版本/权限的缓存键及可观测的降级标记。

## 分层记忆：控制上下文增长

近期消息进入 Redis；摘要、情景片段与画像进入 Chroma。工作记忆 TTL 为 24 小时，15 条消息触发压缩，保留最近 5 条；不是 15 轮对话。

好处是控制上下文体积，代价是摘要损失信息。24 小时 TTL 不覆盖全部长期数据，不能据此承诺所有个人信息自动删除。生产需补充删除、导出、保留策略和摘要版本。

近期工程修复使用用户/会话 `$and` 条件、同用户补充检索及画像 upsert，并以真实 Chroma 集成测试验证。

## Skills：业务 SOP 与代码解耦

Skills 按角色及关键词匹配后加入 system prompt，支持热加载和字符预算。它是业务规则文本，不是可执行插件，也不能提供强制授权。

关键权限必须由代码校验；规则冲突、长文本截断与恶意知识内容仍可能影响模型，应保留版本、审阅和回归测试。

## 观测与评测：发现问题而非宣传数据

在线统计帮助定位超时、失败与降级；离线意图指标和四维 Judge 帮助比较版本。

当前默认不启用独立 Prometheus server 时，自定义业务指标没有完整注册；`/metrics` 可访问不等于已覆盖业务埋点。每类 Agent 默认单实例，也不能将路由惩罚描述为生产自动容灾。

Judge 有偏差且可能解析失败。功能测试通过、默认用例通过率与真实业务准确率是不同概念，需在[评测方案](评测与优化.md)中分开报告。

## 部署：区分开发与公网演示

本地 Compose 提供多容器和持久化目录；公网演示把前端与 API 放在同源网关之后，增加签名 Cookie、限频和管理接口隔离。免费实例的临时文件系统和单并发决定它仅适合演示，不是生产扩容方案。
