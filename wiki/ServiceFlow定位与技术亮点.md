# ServiceFlow 项目定位

ServiceFlow 是面向客服问题处理的多 Agent 编排系统。目标是让一次服务请求的分流、知识依据、执行边界、上下文与异常处理可以检查，而不只是得到一段回答。

## 适用场景

- 通用咨询：澄清需求、识别订单或账户相关信息。
- 技术支持：解释错误码，整理排障步骤，提示补充运行环境。
- 账单服务：核对用户提供的字段与金额，说明示例退款规则。
- 复杂诉求：同时出现登录故障和重复扣款时，由专业角色分别处理后合成。
- 人工交接：输出结构化摘要和升级标识，供后续业务系统接入。

## 当前实现

HTTP 层使用 FastAPI。角色编排、RAG、记忆、Skills、工具可靠性和质量评测均由仓库 Python 代码实现；前端为原生 HTML/CSS/JavaScript，未采用 React 或 Vue。

模型默认通过 Anthropic Messages 兼容协议访问 DeepSeek。多个 Agent 指不同角色、工具权限和执行路径，并不代表部署多个不同的基础模型。

知识库与长期记忆使用 ChromaDB，工作记忆使用 Redis。独立数据库服务不可用时，Chroma 可转为本地持久化；这不是数据库副本或自动数据同步。

## 能力边界

没有真实订单、支付、退款和工单平台集成；金额计算不证明交易事实，人工升级标识不代表有人已接单。

没有训练或微调基础模型，没有生产多租户认证和 RBAC，也没有可信的大规模在线压测结果。公网登录只是演示网关保护，本地原始 API 不应直接暴露。

`mcp/` 是内部工具层目录名，不是已经发布的标准 MCP 服务。监控路由惩罚接口已存在，但默认每类角色只有一个实例，不能声称实现了生产级自动故障切换。

## 项目价值如何证明

通过混合意图的路由字段、请求级工具轨迹、真实 Chroma 集成测试、独立部署与固定评测集证明具体能力。检索质量、成本和延迟应使用实验报告表达，而不是在功能列表中填写未经验证的提升比例。
