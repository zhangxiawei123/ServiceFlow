# ServiceFlow 项目展示与面试

## 项目标题

ServiceFlow｜多 Agent 客服编排与知识服务系统

## 可核验的项目介绍

ServiceFlow 使用 Python/FastAPI 提供对话 API，通过角色路由、白名单工具、ChromaDB 知识检索和 Redis/Chroma 分层记忆处理通用、技术及账单诉求，提供独立聊天页面、请求级工具轨迹和受保护的云端演示。

这描述的是系统能力，个人贡献应进一步限定为实际负责和能够解释的内容。源码来源见[来源说明](../PROVENANCE.md)，不能因仓库改名而声称全部基础代码从零原创。

## 个人工作表达模板

按实际参与范围选择，不要求全部采用：

- 完成模型兼容接入与配置验证，通过 Anthropic Messages 协议调用 DeepSeek，并补充配置回归测试。
- 完成聊天工作台与云端演示入口，使用签名 Cookie、请求限制和管理路由隔离保护模型调用额度。
- 修复 Chroma 情景记忆多条件过滤，保持同用户检索范围；使用 upsert 更新画像，并增加真实数据库集成测试。
- 梳理 Agent 路由、知识检索与分层记忆链路，编写部署、故障排查及评测文档。
- 若后续亲自完成检索优化：附带实验版本、样本量、前后指标、费用和延迟，再加入相应成果。

不要把“熟悉”“调试”“实现”“设计”当作可互换动词，也不要把助手代做而未理解的代码描述成可以独立讲清楚的经验。

## 数据成果的写法

没有报告时，写“建立评测方案”“增加测试覆盖”“完成真实链路验证”。有报告时使用：

> 在固定的 [样本数] 条测试集及 [知识库版本] 上，将 [指标] 从 [基线] 改善到 [结果]，同时记录 P95 为 [实测值]、每次平均费用为 [实测值]。

方括号是待填写项，不是建议捏造的数值。测试数量不等于业务正确率。

## 前端经历如何写

可以写“提供原生 HTML/CSS/JavaScript 演示工作台，调用同源对话与轨迹接口”。如果主投后端/Agent 实习，将重点放在 API、编排、记忆、质量验证和部署，不写未使用的 React、Vue 或复杂前端工程能力。

## 展示顺序

1. 一分钟说明场景、架构与能力边界。
2. 演示一个知识问题和一个混合诉求。
3. 展示 request_id 对应的工具轨迹。
4. 展示一项具体故障、修复和回归测试。
5. 说明当前限制及下一项实验。

问到代码来源时如实说明初始代码与后续工作；问到没有完成的优化，用“计划”“待验证”而不是“已经提升”。
